01 · Access governance

Self-service access with controlled provisioning

A Slack-based access platform that turns fragmented requests into configurable, auditable workflows across dozens of applications.

Internal production system

Problem

Application access was distributed across informal messages, manual follow-up, and inconsistent provisioning paths.

System

  • Self-service Slack requests
  • Per-application approval chains
  • Automated group-based provisioning
  • Email-security actions and scheduled reviews

Safety design

  • Writes disabled by default
  • Explicit production gates
  • Human approval for sensitive access
  • Configuration separated from workflow logic

Node.js · TypeScript · Slack Bolt / Socket Mode · Okta APIs · Email-security APIs

02 · Identity lifecycle

Lifecycle automation with independent reconciliation

A scheduled account state machine for onboarding, active employment, and offboarding, paired with a separate read-only control that detects cross-system drift.

Live automation

Lifecycle engine

  • Routes new accounts through controlled states
  • Moves active users based on validated attributes
  • Removes terminated users from group access
  • Excludes protected service and guest accounts

Control layer

  • Read-only comparison across identity and collaboration systems
  • Specific mismatch reporting
  • Independent credentials and minimal scopes
  • No automatic remediation by the recon job

Reliability

  • Idempotent repeated scans
  • Explicit state precedence
  • Action and error logging
  • Human-readable operational digests

Google Apps Script · Admin SDK · Okta OAuth service apps · Slack APIs · Google Workspace

Architecture principles

Patterns shared across the systems

Safe defaults

Potentially destructive writes begin disabled or dry-run and require deliberate enablement.

Least privilege

Read-only jobs use read-only service identities rather than inheriting broader administrative scopes.

Human control

Automation handles repeatable work while preserving review for privileged, ambiguous, or destructive actions.

Idempotency

Scheduled jobs can run repeatedly without reapplying settled state or creating duplicate side effects.

Observability

Actions, failures, pending work, and cross-system inconsistencies are surfaced in useful operational summaries.

Usable security

Controls are embedded into tools employees and administrators can actually use, rather than added as separate friction.
